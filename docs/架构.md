## 一、总体架构

本地单进程的对话型 Agent，采用 **MVC + Service（"MVC+S"）分层**：

```
View（网页 index.html ／ CLI openai_hello.py）
        │  HTTP（fetch / SSE）            │  函数调用
Controller（app/controllers/，FastAPI 路由）
        │
Service（app/services/chat_service.py，ChatService 单例）
        │
Model（app/models/：Personality / UserProfile / WorldBook / MemoryStore+db / EmotionTracker）
        │
配置层（app/config.py，全部常量与环境变量覆盖）＋ 工具层（app/utils/：clock、weather、llmjson）
```

两个 View（网页、CLI）共用同一个 `ChatService`，命令逻辑只存在一份；Controller 只做入参校验、调 Service、包响应，不写业务判断；Model 层不感知调用方（Web、CLI、基准脚本都能用）。

## 二、各层职责

### 网页 View（2026-09-28 更新）

原生 HTML + TailwindCSS + ES Modules。`api.js` 负责账号密码提交、自动保存令牌、会话验证、服务端退出、401 凭据清除与请求取消；
`app.js` 组织登录、聊天、侧边导航和五个记忆页；`sse.js` 用本地 eventsource-parser 解析分包；
`audio.js` 用 MediaSource 播放，失败时保留全部音频分片并回退 Blob。
`npm run build:frontend` 编译本地静态资源，FastAPI 的托管方式保持 `/` + `/static`。
`/api/healthz` 的 `password_login`、`account_setup_required`、`legacy_data_available` 控制登录与本机首次创建账号。缺少密码登录接口的旧进程会显示重启提示。
`auth.py` 用 PBKDF2-HMAC-SHA256 保存密码，登录签发 7 天的随机令牌；`accounts.data_uid` 可把首个本机账号绑定到原默认数据。registry 以物理数据身份缓存、借出和释放，因此绑定账号与默认用户共用实例。

### Controller 层（`app/controllers/`）

HTTP 进出口。`chat_controller.py` 提供：

| 接口 | 方法 | 作用 |
|---|---|---|
| `/api/auth/setup` | POST | 本机/管理员首次创建账号，可关联原默认记忆 |
| `/api/auth/login` | POST | 后端验证账号密码并签发令牌，连续失败限流 |
| `/api/auth/me` | GET | 验证 Bearer 令牌并返回实际账号名 |
| `/api/auth/logout` | POST | 吊销当前会话令牌 |
| `/api/state` | GET | 状态栏数据（模型、人设、画像、记忆统计、世界书）。开场白只回缓存值 |
| `/api/greeting` | GET | 页面打开/刷新时按最新记忆**重新生成**开场白（`force=True`） |
| `/api/chat` | POST | 非流式一轮对话 |
| `/api/chat/stream` | POST | 流式一轮对话，SSE **五种事件**：`meta`（召回）→ `delta`（正文）→ `done`（记忆/画像备注）→ `audio`（音频分片 base64）→ `audio_end`（音频收尾）。语音在 `done` 之后推，前端 MediaSource 边收边播 |
| `/api/feedback` | POST | 「她说错了」：把**上一轮的完整现场**追加到 `feedback.jsonl`（供事后诊断） |
| `/api/command` | POST | 执行 `/mem` `/world` `/clear` 等斜杠命令 |
| `/api/world`（GET/POST/DELETE） | — | 世界书的查看/手写/删除 |
| `/api/clear`、`/api/forget` | POST | 清会话 / 遗忘长期记忆 |

`schema.py` 用 Pydantic 校验请求体。`app/main.py` 另有 `/`（返回 index.html，禁缓存）、`/favicon.ico`、`/api/health`；其 `lifespan` 除了建 `ChatService` 单例，还在**退出时调用一次 `run_evolve_pending()`**（平时每 20 轮已小步演化过，这里通常没东西；让 `AUTO_EVOLVE_PERSONALITY` 在网页场景也真的生效；失败只打印一行、不影响退出）。

### Service 层（`chat_service.py`，约 700 行）

`ChatService` 是整个应用的编排中枢，持有全部 Model 层对象、三个 OpenAI 客户端与三个感知/输出组件：

- **客户端与组件分工**：`self.client`（后台任务）、`self.chat_client`（主对话）、`self.embed_client`（embedding）；`self.weather`（高德天气缓存）、`self.emotion`（jev 情绪轨迹）、TTS 走 `utils/tts`。三套 OpenAI 凭据与 config 默认相同时直接复用同一实例。
- **职责**：
  1. `system_prompt()` —— 每轮重新组装 system 段（当前时间 → 天气 → 用户最近情绪 → **当前状态（slots）** → 性格模板 + 用户画像）
  2. `prepare()` / `ask()` / `stream()` / `finish_turn()` —— 一轮对话的编排；`finish_turn` 里触发增量性格演化（`EVOLVE_EVERY` 轮）、画像更新、天气刷新与情绪记录
  3. `speak_stream()` / `speak()` —— 语音合成（流式 / 收全版），失败静默
  4. `greeting()` / `_make_greeting()` —— 从记忆生成开场白（约定先判状态：**已过的不邀约**，问候必须符合当前时段）
  5. `run_command()` —— `/personality` `/world` `/user` `/profile` `/clear` `/mem` `/forget` `/timeline` `/slots` `/fix`（事实类反馈修正）`/city`（城市查看 / 显式定位）的统一解析
  6. `run_evolve_pending()` —— 性格小步演化的统一入口：只复盘上次演化之后新增的对话（cursor 机制），周期调用与退出兜底共用；没有新对话不空跑模型
  7. `evolve_personality()` —— 全量复盘式迭代（保留给 `/personality evolve` 手动触发）
  8. `timeline_report()` —— 事件时间轴（`/timeline`）：`event_date` 非空条目按日期倒序，她的条目标〔她〕
  9. `mark_wrong(note)` —— 「她说错了」留证：把 `last_turn`（问题、回答、召回明细、注入的 system 块、模型名）追加到 `feedback.jsonl`；`_recorded_ts` 防连点重复记
  10. `state()` —— 聚合各层状态给前端

现场数据的传递：`prepare()` 把组装好的 messages 与召回结果存进 `_pending_context`，`finish_turn()` 取出后写入 `self.last_turn`，等前端点「她说错了」时由 `mark_wrong()` 取走。**记的是完整现场而不是只记问答**——诊断时要看的是「当时给了她什么」，只看问答分不清问题出在检索、注入还是模型本身。

### Model 层（`app/models/`）

四块数据各管一摊，边界刻意拉开——**用户的事实绝不进性格模板**：

### 工具层（`app/utils/`）

- `llmjson.py`：`chat_json()` / `chat_text()` / `parse_json()`。处理推理模型把 max_tokens 花在思考上导致的空 content（回退读 `reasoning_content`）与截断 JSON（补尾巴），关思考不支持时自动退回。**所有要求模型吐 JSON 的调用共用这里**。
- `clock.py`：时间感知，路线是**写入时换算，读取时不去猜**。
  - `now_text()`（注入当前时间，带星期）；`find_date()`（绝对日期：ISO / 年月日 / 月日，认不出时用 `_REL_WORDS` 兜底认「明天/大后天」这类相对词，长词在前防误匹配）。
  - `find_datetime()`：**时刻级**解析（日期+时刻，含「晚九点半」这类单字时段缩写、中文数字、「半」作分钟；负向断言排除「早一点」「第一名」这类习惯用语）。
  - `describe_when()`：补时距；约定类过期补「已经过期了，不要再说成还没发生」；**时刻级**——今天的约按时段分「已经过了（别再邀约）/还没到（HH:MM）」。
  - `fix_impossible_time()`：**写入哨兵**——完成时句式 + 今天的未来时刻 = 日期锚不可能，回拨到昨天；只动同时满足全部条件的文本。
- `weather.py`：高德天气。**铁律：任何失败都不能挂对话**——`refresh()` 可能联网（启动 + 缓存过期后的后台刷新），`line()` 永远只读缓存；有 last-known-good，连上一次都没有就不注入。设计原则：**工具给事实，人格给话术**——只注入一行事实，不写「下雨就说带伞」的 if-then 话术表。
- `tts.py`：语音合成（`qwen-audio-3.1-tts-flash`，音色「安语晴」），走 DashScope **WS duplex 协议**，**只用 websockets 的同步客户端**（要「边收边 yield」直接对接 SSE 的同步 for 循环）。要点：
  - `script_for()` 生成韵律脚本（SSML），`plain_text()` 剥 Markdown/emoji/方括号标签（纯文本下 `[tag]` 会被服务端忽略但**照旧计费**）；
  - `trim_for_speech()` **按句截断**（在脚本化之前切，不会把标签切一半）；
  - `synth_stream()` 边收边 `yield` 音频块；超时打 WARNING + `stats["timeout"]` 留痕，已产出的音频照常使用；
  - `stats` 记 `conn / first_byte / chunks / bytes / billed`（服务端计费字符）——**分段观测与成本都一样可见**；
  - 语气跟随 jev 情绪轨迹里 1 小时内的 `mood`。

### 基础层（`app/log.py`）

`app.*` 命名空间统一走它：控制台（stderr）+ `DATA_DIR/logs/app.log`（`TimedRotatingFileHandler` 按天滚动，默认留 14 天）；uvicorn 的 `error`/`access` 也接进文件（500 的 traceback 在这条上）。级别用 `WB_LOG_LEVEL`（默认 INFO）。**Windows 上必须原地切 UTF-8**（`force_utf8_streams`）——日志流和 print 的 stdout 是两条，只切一条会漏。

### 配置层（`config.py`）

全部常量集中于此；`DATA_DIR` 环境变量可把数据目录整体指到别处（两个评测脚本各用自己的隔离目录）。所有模型名与密钥支持 `WB_*` 环境变量覆盖：`CHAT_NO_THINK`（参数族名 `off` 默认 / `thinking` / `enable_thinking`）、感知（`AMAP_*`、`EMOTION_*`）、语音（`TTS_*`）、演化（`EVOLVE_EVERY`，默认 20）、日志（`WB_LOG_LEVEL`/`WB_LOG_KEEP`）。约束上限 `MAX_CONSTRAINTS=12` 与过期约定过滤 `DROP_STALE_PLANS` 都在它里面（Model 层的 `DEFAULT_CFG` 只是兜底默认值）。

## 三、核心数据流

### 1. 一轮流式对话（`/api/chat/stream`）

```
用户输入
  → Controller: service.prepare(message)
      → store.build_messages(system_prompt, question)
          system 段（system_prompt() 内按序组装）：
          ① 【当前时间】（每轮重新取；含「摘要里的时刻是当时的记录，不代表现在」免疫句）
          ② 【天气】（缓存行，未配密钥则无此块）
          ③ 【用户最近的情绪】（emotion.summary()，没有值得说的就没有此块）
          ④ 【当前状态】（slots 槽位全量，覆盖式更新，上限 12 条）
          ⑤ 性格模板（含自我底座与三级态度预案） + 用户画像
          build_messages 追加：
          ⑥ 【必须遵守的约束】（kind=constraint 且仍生效，每轮无条件注入，不走召回）
          ⑦ 【已经解除的旧禁忌】（relaxed_at 非空的约束：不再当禁令，但保留"有过这回事"）
          ⑧ 【此刻的分寸】（状态槽位派生：命中消失类状态时提醒"默认假设已不成立"）
          ⑨ 【今天说好的事】（upcoming(only_today=True)，上限 3 条，带时刻级状态标签）
          ⑩ 【共同生活的世界】（world 类，向量召回 top 3）
          ⑪ 【想起来的事】（fact/turn 类，向量召回 top 3，带时距/过期标注）
          ⑫ 【更早之前】滚动摘要（若有）
          ⑬ 滑动窗口内最近 10 轮原文（window=10，跳过空回答）
          ⑭ 本轮 user 消息
  → SSE meta 事件（召回明细回给前端）
  → service.stream()：chat_client 流式生成，逐字 yield → delta 事件
  → 完整收到正文后 finish_turn()：
      store.add_turn(问, 答)   ← 记忆写入管线（见 2）
      store.save()             ← 增量落盘
      每 EVOLVE_EVERY(20) 轮触发 run_evolve_pending()   ← 性格小步演化
      每 5 轮触发 profile.analyze()                      ← 用户画像更新
      后台跑 weather.refresh() / emotion.record()        ← 感知层更新，不影响首字
  → done 事件（memory_note / profile_note）
```

注意：**前端中途断开时生成器被关闭，该轮不会写入记忆**（Controller 注释明确说明）。

### 2. 记忆写入管线（`MemoryStore.add_turn`，每轮在 `finish_turn` 中触发）

```
add_turn(用户, 助手)
  ① 追加进会话历史（内存 + 待落盘）
  ② _maybe_summarize()：窗口外攒够 summarize_every(6) 轮 → 滚动摘要
     （SUMMARIZE_PROMPT 硬规则：不把「当时几点」写进摘要——长生命周期存储里的
       时刻必然过期变成错误信息；实际咬过人：摘要里冻着「晚8点31分」，
       下午三点她说「晚安」）
  ③ 显式通道：用户说了「记住 xxx」触发词 → 原话直接入库（kind=fact, explicit=True），
     不经提炼器取舍；explicit 条目不参与容量淘汰
  ④ _extract()：调提炼模型，输出六类——
       facts        事实短句（用户侧）
       world        世界书新条目（只写没有的；只收长期成立的，一次性事件走 facts）
       constraints  硬性约束（每轮常驻注入的一类）
       drop         被这轮明确推翻的旧条目原文（只认库里真实存在的原文）
       selfs        她的经历（第一人称「我…」，只认「我」开头防串层；
                     纪律：只能从实际说的话/做的事提炼，不许脑补）
       slots        当下状态变化（entity/attr/value 三键齐全才收，覆盖式写入 slots 表）
     提示词里喂了：现有世界书+约束（防重复）、相关旧记忆（发现推翻）、
     最近作废条目（防复活）、当前时间（相对时间换算成绝对日期）
     提炼失败返回 None——**失败分支必须返回同样 6 个位置**：踩过，失败分支少写两个
     位置，于是"提炼失败"这条本该被容忍的路径变成整轮 ValueError、SSE 收尾跟着断。
  ⑤ drop_memories(drops)：**按 kind 分流**——约束走「解除」（标 relaxed_at，不删不归档，
     因为它没有被推翻、只是不再生效），其余走作废归档（软删 archived_at）
  ⑥ _add_memories()：新条目分别入库；写前查重（普通相似度 ≥ dedup_sim=0.92 判重）；
     写入哨兵：clock.fix_impossible_time()——完成时句式 + 今天的未来时刻
     = 日期锚不可能，回拨到昨天（实测抓过「晚上九点半已没再疼」写于 19:50 的错锚）。
     入库时跑 clock.find_date() 存结构化 event_date（解析不出为 NULL，不硬造）；
     selfs 走 actor="assistant"，其余 actor="user"；
     被世界书/约束覆盖的普通条目就地"转正"改 kind。
     world 类另走 _world_check() 三态判定：duplicate（≥0.86 直接判重，否则交模型判）
     / contradict（写新的 + 作废被推翻的旧条目）/ new；条目 ≤ WORLD_FULL_REVIEW(30) 时
     全量复核一次，因为互斥的两句相似度可能只有 0.50，靠阈值筛候选永远筛不出来。
     **作废发生在新条目落库之后**，否则会出现「旧的没了、新的也没写下」的空窗
  ⑦ _compensate()：作废补偿——问一次模型"旧条目里还有哪些仍然成立"，
     捡回被整条作废连坐的信息
  ⑧ 第二道兜底：新事实含状态变化词（搬到/换成/戒了…）但没触发 drop 时，
     _find_superseded() 主动追问"哪些旧记忆被取代了"
  ⑨ on_world 回调 → WorldBook 把新 world 条目写回 world.json（保持唯一真相）
  ⑩ event() 埋点：把这一轮的账记进 events 表（提炼条数 / 世界书三态 / 补偿捡回 /
     兜底命中 / 作废与解除 / 摘要推进），用 `/mem events` 看聚合计数与最近明细。
     埋点自身全包 try/except——**它绝不允许影响主流程**
```

### 3. 向量召回（每轮 `build_messages` 内）

查询文本 → `_embed()`（embedding 客户端）→ 与内存中的 numpy 矩阵做余弦相似度（`_sims`）→ 按 kind 过滤 + top_k + 阈值（`threshold=0.45`）→ 贴线的条目标「（弱相关）」（让模型自己权衡，别默默顶掉真正相关的）→ 命中计数 +1（攒到 `save()` 批量落盘）。

两个额外规则：
- **过期约定不参与召回**（`drop_stale_plans=True`）：过期 + 承诺类词 + 未完成 → `_is_stale_plan()` 挡掉，不再冒充待办抢 top_k。数据仍在库里，时间轴照旧可见。
- **一轮只发一次批量 embedding**（`#014`）：召回、写入查重、世界书判定共用同一批向量，不再按条往返。

启动时全部活跃行向量从 SQLite BLOB 拼成连续矩阵；缺向量的行由 `_recover_missing_vectors` 自动补算。

### 4. 遗忘与淘汰

- 权重 = (1 + 命中加成) × 时间衰减（半衰期 `half_life_days=30`）。
- 超过 `max_memories=2000` 时淘汰权重最低的；**world / constraint / explicit 条目不参与**。
  注意可淘汰候选只是活跃集的子集：「超限条数」未必等于「能删条数」，删不够时打一条 WARNING
  ——上限达不成必须是**显式**的，不许静默失效。
- 作废 = 软删归档（`archived_at`，上限 `archive_keep=500`，超限删最老的）；只有用户明确意图（`/mem del`、`/forget`）才物理删。
- **约束不走作废**：被放宽时标 `relaxed_at`（"已解除"）——留在活跃集里留档，只是不再是禁令。
- **状态槽位不参与淘汰**：数量天然有限（实体 × 属性）。
- **事件流水 `events` 只增**：超 `events_keep=5000` 时在 `save()` 里修剪最老的（每轮一次，不做成"每次写入都 COUNT(*)"）。

### 5. 世界书同步（双向）

```
world.json（手写，唯一真相）--启动 sync()--> 向量库（kind=world）
向量库提炼出的新 world 条目 --on_world 回调--> world.json
对话判定作废且命中 world 条目 --on_drop 回调--> 从 world.json 删除
```

`WorldBook.__init__` 里的 `_absorb_store()` 先回收向量库里已有但 json 里没有的条目，防止 sync 把它们误判成"文件里已删除"而清掉。

### 6. 开场白

页面打开/刷新 → `GET /api/greeting` → `greeting(force=True)`：先清掉上一条开场白（避免堆满滑动窗口），再用 GREETING_PROMPT（含今天及未来 7 天的约定、世界、事实、上次结尾、聊天间隔）生成一句 ≤30 字的开场白，写回会话历史。约定标签是**时刻级**的：今天的约会标注「约定时刻已过，别再邀约」；提示词硬规则——已过或已有结果的约定**绝不邀约**（最多轻轻回顾），确实没发生才催促，拿不准就不提；问候必须符合当前时段（修过「晚上八点催早上十点的约」的实际事故）。记忆全空时回退 `personality.json` 的固定开场白。`/api/state` 只返回缓存值，不重复生成。

### 7. 感知层（回答之后后台跑，不影响首字）

`finish_turn()` 里：天气缓存过期就 `weather.refresh()`（失败静默）；按 `EMOTION_EVERY` 周期调 `emotion.record(question, 上下文)`，经 jev 判情绪，conf<0.6 或失败都不记录。下一轮的 `system_prompt()` 里注入【天气】与【用户最近的情绪】——工具只给一行事实，话术交给人格。

### 8. 语音（文字先上屏，声音随后到）

顺序由 Controller 保证：`delta` 事件推完 → `done`（记忆/画像备注）→ 才轮到音频。`/api/chat/stream` 里对 `service.speak_stream()` 逐块 `yield` `audio` 事件（base64），结尾是 `audio_end`；前端用 MediaSource **边收边播**（实测服务端首字节 0.7s，等收完再发就进不了 1 秒级）。TTS 全流程包在 try 里，失败只打 WARNING，**文字对话不受任何影响**。语气取自情绪轨迹里 1 小时内的 `mood`。

### 9. 性格演化（小步迭代）

`finish_turn()` 里每 `EVOLVE_EVERY`（默认 20）轮调 `run_evolve_pending()`：用 `_evolved_pos` 游标只复盘**新增**的对话（曾踩过「消息数 ×2」的双重计数 bug 导致演化静默失效，靠插桩抓到）；退出时 lifespan 兜底调一次，没有新对话不空跑模型。输出走后台模型 + JSON 兜底，白名单过滤后写回 `personality.json`。

⚠️ 已知缺口：**演化没有一致性检查**。一次演化给 `behavior` 加的新条目可能与 `traits` 里的旧条目方向相反（实测：新增「别动不动讲道理」vs 原有「热心，先帮你想办法」），人格层不像记忆层那样有 `_world_review` 挡着。目前仍待补一致性检查。

### 10. 人格评测（四件套，不打分）

`benchmark/run_persona.py` + 13 条手写探针。每条探针给 3~4 个**互斥类别**（可归因、可计数），再叠加三项：② **强迫选择**（有人设 vs 无人设两段回答，随机左右顺序、允许平手）③ **辨识测试**（人设摘要 + 三段回答里挑出她的，随机基线 1/3）④ **矛盾检测**（多条回答里找互相排斥的说法）。
**明确不打 1–5 分**——同一条探针重复测量时裁判给过 5 也给过 4（噪声 0.5~1.0），任何小于噪声的 delta 都不成立；而且分数会把「她否认了人格」和「她列点用了编号」压成同一个数字。`persona_cases.json` 里留了 `why_not_score` 说明。

## 五、存储层细节（`memory.db`）

SQLite，`journal_mode=WAL`，`synchronous=NORMAL`。**十二张表**（另有 SQLite 自建的 `sqlite_sequence`）：

| 表 | 结构要点 |
|---|---|
| `memories` | 一条记忆一行；**向量以 BLOB 存同一行**（`vec` 列），不再有平行数组；`archived_at`/`archived_reason` 实现软删归档；`event_date TEXT`（事件日期，入库时 `find_date` 解析，NULL=无日期）；`actor`（user/assistant，她的经历条目走 assistant）；`relaxed_at REAL`（约束失效时刻，NULL=仍生效）；两个索引（活跃集合、按 kind）。新列靠 `connect()` 里的 PRAGMA 检查 + `ALTER TABLE` 迁移（`CREATE TABLE IF NOT EXISTS` 不会给旧表补列） |
| `messages` | 会话消息，主键 (session, seq)；`greeting` 标记开场白消息 |
| `summaries` | 每 session 的滚动摘要 + 已摘要游标 cursor |
| `pending` | 暂无向量的记忆（embedding 不可用时兜底，下次启动补算） |
| `slots` | 状态槽位，主键 (entity, attr)：覆盖式更新「现在是什么样」。和叙事记忆分工——年糕在哪不该靠相似度碰运气。注入时全量（上限 12 条），并派生出【此刻的分寸】 |
| `events` | 机制埋点流水（append-only）：`ts/kind/session/payload`。回答「补偿真的有效吗」「兜底触发率多少」这类问题；靠 `events_keep` 修剪最老的 |
| `meta` | 键值（目前存迁移来源标记 `migrated_from`） |

并发模型：FastAPI 同步接口跑在线程池，而 `ChatService` 在 lifespan（主线程）创建——连接必须 `check_same_thread=False`；多语句事务的互斥由 `MemoryStore._lock`（`threading.RLock`）保证。

**写路径已全面收锁**（2026-09-23/27 两次并发审计）：`vectors`/`memories` 的成对写入、命中计数自增、作废、约束解除，分别收进 `_attach_vector()` / `_mark_hit()` / `_drop()` / `relax_constraints()` 四个入口，锁外不再直接改共享状态；审计时顺带抓到一个「召回直接 500」的真 bug（`_sims` 同一表达式里两次读 `self.vectors`，中间可能被换掉）。
**读路径有意不加锁**：召回只读内存矩阵与快照，加锁只会把吞吐压下去而换不到正确性——这是刻意划的边界，测试用例里有并发混合操作的用例守着它（改动过锁或共享状态就要先跑一次）。

写入是增量的（INSERT/UPDATE 单行），`save()` 只补命中计数、新消息、摘要三类脏数据，事件流水在 `save()` 里修剪（每轮一次，不做成每次写入都 COUNT(*)）。旧 JSON+npy 格式由 `db.migrate_from_json()` 一次性迁移，原文件改名 `*.migrated` 保留。
