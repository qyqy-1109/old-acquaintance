# DECISIONS.md · 关键决策记录

> 这份文件回答一个接手者或评审者最想问的问题：**为什么这么做**。
> 每条决策都给出「背景 → 决定 → 依据 → 被否决的替代方案 → 代价」，依据尽量落到**代码位置或实测报告文件**上，方便当场核对。
> 最后更新：2026-09-23（深夜：新增 D18–D20）。数字都来自 `benchmark/results/*.json`、本仓库的实测脚本或 `tests/test_pure.py` 的真实输出，未做估算。

## D1. 记忆分四层，按「谁能写」划权

**背景**：一开始所有东西都往一个「记忆」里塞，结果是用户的事实会污染 Agent 的自我认知——她开始把「用户养了猫」当成自己养了猫。

**决定**：拆成四层，各层区别不是「装什么」而是**写权与生命周期**：

| 层 | 谁能写 | 生命周期 |
|---|---|---|
| 性格 `personality.json` | 只走白名单字段、`name` 与 `scope` 不可被对话修改 | 每次迭代留快照，可回滚（最多 20 版） |
| 世界书 `world.json` | 人工可写（唯一真相），程序只在提炼出新设定时追加 | 不参与遗忘 |
| 用户画像 `user_profile.json` | 独立分析模型每 5 轮覆写 | 只增不删 |
| 对话记忆 `memory.db` | 提炼器追加 + 作废通道 | 有遗忘与容量淘汰 |

**依据**：`app/models/personality.py` 的 `EVOLVABLE` 白名单（`name`/`scope` 刻意不在其中）+ `_sanitize()` 的三道护栏（字段白名单、必须含中文、单次不许砍掉一半以上）；`app/models/__init__.py` 的层职责说明。

**被否决的替代**：让模型自己决定往哪层写。实测会把用户属性写进 `behavior`，人设被对话同化。

**代价**：跨层一致性没有单一真相源，各层会慢慢互相矛盾——所以必须有 D12 的跨层对账。

## D2. 长期记忆存「提炼后的短句」，不存对话原文

**背景**：存原文时，召回回来是一大坨，有用信息被寒暄稀释；而且「我叫小林」这种事实必须跟当时整段对话绑在一起才找得到。

**决定**：每轮额外调一次提炼模型，只把**事实短句**入库（`fact` 类型），原文另存会话历史、只在滑动窗口内进模型。

**依据**：`EXTRACT_PROMPT`（`app/models/memory.py`）+ 配置 `threshold=0.45`（注释记录：存原文时 0.30 都嫌松，存短句后必须收紧）。

**被否决的替代**：`AUTO_EXTRACT=False` 直接存整轮原文——保留为可回退的开关，但默认关闭。

**代价**：每轮多一次模型调用（实测单次提炼 1.7~2.5s，发生在回答之后，会延后 SSE 收尾）。

## D3. 「约束」不靠召回，每轮无条件注入

**背景**：评测 B05 实测——问「给我推荐点零食吧」时，召不回「我对花生过敏」。两句没有任何字面重叠，纯向量检索必然失效。

**决定**：把硬性要求/禁忌单列为 `constraint` 类型：**不参与召回、不参与遗忘、不参与容量淘汰**，每轮无条件注入 system 段，并设上限 `max_constraints=12`（超了只留最近的）。

**依据**：`app/models/memory.py` 的 `KIND_CONSTRAINT` 注释与 `constraints()`；`build_messages()` 里【必须遵守的约束】区块。上限实测有效：库里 17 条约束时实际只注入 12 条。

**被否决的替代**：把约束混在普通事实里靠召回碰运气——这是原始实现，B05 就是它失灵的现场。

**代价**：约束不参与召回，所以它**永远不会因为「语义相关」被强化**；上限 12 条也意味着攒多了会挤掉最早的约束。

⚠️ 注意：`max_constraints` 只写在 Model 层的 `DEFAULT_CFG` 里，`app/config.py` 的 `MEMORY_CFG` 没有覆盖它。想调整得改 `memory.py`，这在 config 里看不出来——属于已知的配置分散问题。

## D4. 作废要软删归档，且作废后必须做一次「补偿」

**背景**：实测 5 个场景，**2 次真的丢数据**。最严重的场景：世界书「用户住在杭州，养了只叫年糕的橘猫」，用户说搬到成都后，整条被作废——**猫一起没了**，连新地址都没记住。

**决定**：三层防护
1. **软删归档**：对话里判定被推翻的条目只标 `archived_at`，不物理删（`archive_keep=500` 兜底）。
2. **作废补偿** `_compensate()`：作废后问一次「旧条目里还有哪些仍然成立」，把被连坐的信息捡回来。
3. **第二道兜底** `_find_superseded()`：新内容（含用户原话）命中状态变化词时，主动追问「哪些旧记忆被取代了」。

**依据**：`_drop(archive=True)`、`_compensate()`、`_find_superseded()`、`STATE_CHANGE` 正则（覆盖替换式/结束式/放宽式三类失效）。效果：补偿后 5 个场景全对；作废触发率实测 **0/4 → 4/4**。

**被否决的替代**：只在提示词里写「不要整条作废」——实测模型 40% 不听。**结论：涉及删改的可靠性不能只靠提示词，必须在模型之外补机器兜底。**

**代价**：每次作废多一次模型调用（作废本身不常发生）；归档条目留在库里占空间（实测 500 条约几 MB，不是性能问题）。

## D5. 世界书以 JSON 为唯一真相，入库时查「矛盾」而不只查「重复」

**背景**：世界书条目少而重要，但更新会以「矛盾」的形式出现——两条讲同一主题却互相排斥。

**决定**：
- `world.json` 是唯一真相、可手写；启动 `sync()` 灌进向量库；提炼出的新条目经回调写回 json。
- 入库走**三态判定**：`duplicate`（丢）/ `contradict`（写新的 + 作废旧的）/ `new`。
- **条目 ≤ 30 条时直接全量复核**，不靠相似度筛候选。

**依据**（这是本项目最有价值的一条实测发现）：`_world_check()` 的注释与 `WORLD_FULL_REVIEW = 30`。实测「养了只叫年糕的橘猫」vs「家里没有养任何宠物」相似度只有 **0.50** —— 语义互斥的两句字面几乎不重叠，**任何合理的相似度阈值都拦不住**。所以不能「先按相似度挑候选、再判矛盾」，只能全量复核。

**被否决的替代**：单纯压低相似度阈值。实测两条合法且各自独立的设定也能有 0.73 相似度，压低了会误杀。

**代价**：世界书条目多到超过 30 条时退回相似度近邻（准确率下降），且每次入库多一次模型调用。另外模型说「矛盾」但给不出具体原文时会退化成「新增」——不敢凭一句结论删旧条目。

**顺序约束**：作废必须发生在新条目落库**之后**，否则会出现「旧的没了、新的也没写下」的空窗（`_add_memories` 里 `world_conflicts` 攒起来最后处理，就是为了这个）。

## D6. 相对时间在**写入时**换算成绝对日期

**背景**：「明天早上九点开会」存成原文，过两天就废了——「明天」永远指向说话那一天。

**决定**：
- 每轮注入【当前时间】到 system 段（每轮重新取，不能启动时算一次冻住）。
- 提炼提示词里给当前时间，并要求把相对时间换算成绝对日期（习惯性重复如「每天七点跑步」不换算）。
- **读取时不去猜**：不在召回阶段解析「下周三」是哪天。
- `clock.find_date()` 另配 `_REL_WORDS` 兜底（长词在前，「大后天」不被「后天」抢先匹配），并做了「绝对日期优先于相对词」的断言。
- 约定类条目过期后，`describe_when()` 显式补「已经过期了，不要再说成还没发生」；历史事件不追加这句。

**依据**：`app/utils/clock.py`；`tests/test_pure.py` 里 4 组用例（跑 `python tests/test_pure.py` 全部通过）。**相对词兜底是单元测试抓出来的真缺口**：原来 `find_date` 完全不认「明天/后天/今天」，一旦提炼器漏了换算，这条约定对时间系统就完全隐形（`upcoming()` 捞不到、不标注时距），用户永远等不到提醒。

**被否决的替代**：读取时解析相对时间——时间一过必然算错。

**代价**：依赖提炼器写成可解析的格式（「本周三」「明早」抠不出来）；一个条目只认第一个日期；表达不了区间。

## D7. 存储层从「JSON + npy」换成 SQLite（先量成本再决定）

**背景**：旧方案是「每次保存全量重写 JSON + 向量矩阵」，且 `memories` 与 `vectors` 是两个平行数组靠下标对齐——改动时漏同步一个就**静默错位**，这个坑已经踩过一次。

**决定**：SQLite，一条记忆一行，**向量以 BLOB 存在同一行**；启动时把活跃行向量拼成一个连续矩阵，运行时召回仍是内存里的矩阵乘法。

**依据**：`app/models/db.py` 的模块注释记录了实测——20000 条 × 2048 维：读连续 npy 文件 66ms、读 SQLite BLOB 拼矩阵 382ms，**差 315ms 且只在启动时付一次**；按实际规模（2000 条以内）差距约 30ms。换来的是「下标错位」这个风险类别彻底消失。

**被否决的替代 / 修正过的话**：早期判断「全量重写会随规模变成瓶颈」——实测 20000 条全量写也只有 422ms，而每轮对话要等 1~20 秒的 LLM，**全量重写根本不是瓶颈**。所以搬迁的理由不是性能，是**消除静默错位的风险**与**让软删归档可行**。

**代价**：并发正确性要自己保证——`check_same_thread=False`（FastAPI 同步接口跑线程池，而 `ChatService` 建在主线程）+ 一把 `RLock` 守多语句事务。踩过的坑：`np.frombuffer` 返回只读视图，重启后任何就地写向量都会崩（已加 `.copy()`，且这个 bug 只在重启后出现，第一次启动不触发）。

## D8. 召回用向量，不用 FTS5 关键词检索

**背景**：曾有一个更「轻」的方案：用 SQLite 自带的 FTS5 做关键词检索，省掉 embedding 依赖。用户当时也要求换成这个。

**决定**：保留向量召回。

**依据**（用 10 组「真实记忆 ↔ 真实探针」对照实测）：

| 方法 | 正确条目排第一 |
|---|---|
| 向量（现用） | **7/10** |
| trigram + OR | **0/10** |
| bigram（人工 2 字滑窗）+ OR | 4/10 |
| unicode61（默认） | 0/10 |

根因：10 条里 **6 条探针和记忆之间没有任何两字重叠**——这是关键词检索的死结，换分词器救不了。而且 bigram 命中的那 4 条向量全都命中了，**两者无互补性**，做混合检索在这批数据上增量为 0。

**测试自身踩的坑（值得单独记）**：第一版测出 trigram/bigram 都是 0/10，差点据此下结论。实际是 **FTS5 对空格分隔的词默认是 AND**，等于要求「查询的每个 n-gram 都必须出现」。必须显式写 `OR`。**凡是测检索，先确认查询语义是 AND 还是 OR。**

**代价**：引入了 embedding 依赖与维度耦合（换 embedding = 换维度 = 必须 `UPDATE memories SET vec=NULL` 重算，启动时自动补算）。

## D9. 主对话与后台任务分开配置，三套独立客户端

**背景**：首字延迟是唯一体验瓶颈。拆开计时（`_tmptest/t_latency.py`）发现：召回 + 组装的准备阶段只要 0.29~0.31s，而**首字延迟 7.73s / 24.39s / 10.36s，占单轮总时长 80~86%**。根因：思考全部发生在第一个可见字之前，且思考内容不走 `content` 流，用户只能干等。

**决定**：
- 三套客户端分离：`client`（后台活）/ `chat_client`（主对话）/ `embed_client`（embedding）。凭据未单独配置时复用，行为不变。
- 主对话关思考：`CHAT_NO_THINK="thinking"` → `extra_body={"thinking": {"type": "disabled"}}`（默认值另立常量 `CHAT_NO_THINK_DEFAULT`）。**`enable_thinking` 族发给 mimo-v2.6-flash 会被静默忽略**（8 样本 reasoning 一次都没归零，`#024`；修复见 `#025`）——所以别按供应商名猜写法，`zhipu`/`qwen` 只作别名保留；后台活用不思考的模型产出 JSON。
- 所有模型名与密钥支持 `WB_*` 环境变量覆盖。

**依据**：`app/config.py` 的选型注释 + `app/services/chat_service.py` 的客户端构建。**关思考有明确代价——第三次复现，这次定位到了受力点**：`#028` 用 8 样本对照，B11（否定式偏好「别给我发长语音，我更习惯看文字」）在**关思考**时规则层漏 `no` **8/8**、最终通过 5/8；**开着思考**是漏 3/8、通过 8/8。提炼层无辜（记忆里存着 `[constraint] 用户要求不要发长语音，以文字形式回复`），问题在回答阶段——约束注入了，但关思考时说不出来。中间 `#025` 用 11 条约束/边界用例对照"看起来没代价"，是因为那批里没有否定式偏好这一类——**代价只落在特定题型上，拿错题型做对照就会得出"没代价"的错结论**（这条方法论本身值得记）。结论：`CHAT_NO_THINK` 默认改为 `"off"`（不关），关思考降级为"想省 0.77s 首字延迟 / 省 reasoning token 时手动打开"的选项。

**速度对照的纪律（吃过三次亏）**：**必须 ≥8 个样本、看中位数 + 最值**。8 样本 A/B 结果——glm-5.3-flashx 首字中位 3.07s / 最慢 8.37s；mimo-v2.6-flash 关思考中位 2.65s / 最慢 **27.35s**。中位数只差 14%，但 mimo 有 1/8 概率撞上 27s 尖峰。此前用 2 个样本得出「快 2.7 倍」的结论是**错的**，已自我修正。

**被否决的方案**：`qwen-flash-character` / `qwen-plus-character`（速度快 5 倍，但约束 0/4、严重编造用户事实，角色扮演模型的固有问题）；`glm-5.2 + 关思考`（0.9s，但超纲题完全不守边界）。46 条全量基线：glm-5.3-flashx CSR 95.7% / 完整率 89.8% / 幻觉 1.9%；mimo-v2.6-flash 93.5% / 94.9% / 1.8%。

## D10. 评测做「规则层 + LLM 裁判」双层，并显式汇报分歧

**背景**：规则层靠别名表判「回答里有没有提到某个事实」，而**别名表只能穷举措辞**。实测踩坑 4 次：她说「花生是雷区」「不额外加糖」「问到我盲区啦」，词表里都没有 → 判成失败，而其实答对了。

**决定**：
- `need_judge = judge_required or not rule_pass` —— **规则层判失败时也让裁判兜一次底**（规则通过的用例不额外花钱）。
- 裁判提示词里明说「措辞不同不算错，按意思有没有达到判断」。
- 逐条显示 `[裁判救回]` / `[裁判推翻]`，并汇总打印不一致条数。**把分歧显示出来，而不是藏起来**——这个数本身就是「规则层有多不可靠」的度量。
- `--rescore <报告>`：用当前规则对已保存的回答离线重评，调规则的 API 成本降为 0。

**依据**：`benchmark/run_bench.py`；同一批回答下，修正判定后 CSR 从 78.6% → **92.9%**（3 条被裁判救回，全是别名漏词）。

**另一条必须记住的**：**静默失灵比显式失败更危险**。一次 `add_turn` 的参数名写错（`question` vs `user`）导致**所有记忆写入全废**，而评测的 `except Exception` 把它吞了、照样跑完出分数，只是每条「召回」都是空的。已加哨兵：注入过轮次却 0 条记忆 → 标「记忆系统疑似失灵，本次结果不可信」并醒目打印。**改完代码先跑一次能暴露「系统整体是否在工作」的检查，别只看分数。**

**代价**：裁判本身也会放水（一次它把「只字未提花生、只是恰好没踩雷」判成「成功避开」）——所以评分尺度必须收紧到「必须显式提到」，不能从结果反推。

## D11. 「她说错了」记的是完整现场，不是只记问答

**背景**：用户反馈某次回答不对时，只看问答无法定位问题——是检索没召回、注入没生效，还是模型不用给它的信息？

**决定**：一键把上一轮的**完整现场**写进 `feedback.jsonl`：`ts / session / model / question / answer / memory_note / recalled（含相似度）/ injected（注入的每个 system 块）/ user_note`。

**依据**：`ChatService.prepare()` 存 `_pending_context` → `finish_turn()` 落 `last_turn` → `mark_wrong()` 写文件；`_recorded_ts` 防连点重复记。前端按钮在 `app/views/index.html`。

**被否决的替代**：只记 question/answer。**理由：只记问答分不清故障发生在检索、注入还是模型**——这正是这套架构里最难定位的一环。

---

## D12. 跨层矛盾只报告，不自动修

**背景**：分层架构没有单一真相源，各层会慢慢互相矛盾，必须有个显式检查。

**决定**：`/mem check` + 启动时自动跑一次跨层对账（stale / conflict / redundant 三类），**只报告、不改任何数据**。

**依据**：`check_consistency()`。自动裁定试过一次，代价是模型把「住在杭州，养了只叫年糕的橘猫」整条删了，**猫也连坐弄丢**。

**代价**：需要人偶尔看一眼面板上的⚠提示。

## D13. 感知层（天气 / 情绪）：工具给事实，人格给话术

**背景**：她不知道今天几度，也做不到「他昨天烦躁、今天没提，该不该主动问一句」。聊天模型单轮内的情绪它自己懂，缺的是**跨天的情绪记忆**。

**决定**：
- `weather.py`（高德）：1h 缓存 + last-known-good，**任何失败都静默**——天气挂了退回上次的好数据，连上一次都没有就不注入。铁律：**天气失败不能挂对话**。
- `emotion.py`（jev，TypeSafe System One 决策模型）：每轮后台判一次用户真实情绪（提示词明说要看穿反讽、口是心非、强颜欢笑），返回**概率 + 置信度**；conf<0.6 不记录；轨迹存 `emotion.json` 只留 14 天；`summary()` 没有值得说的就返回 None——**沉默优于噪音**。
- 注入方式：system 段里各加一行事实块（【天气】【用户最近的情绪】），都在回答之后后台跑，不影响首字。

**依据**：jev 探测 4 个刁钻场景 4/4 全对（口是心非 conf 0.73 / 强颜欢笑 0.90 / 阴阳怪气 0.81），延迟中位 1.14s——专用决策模型干这个比聊天模型强。端到端实测「没事，我挺好的，真的」被看穿并得体收场。

**被否决的替代**：if-then 话术表（「下雨就说带伞」）——那是客服路径，跟「像个人」直接冲突。**工具给事实，人格给话术**是感知层的扩展铁律。

**代价 / 边界**：jev 官方明示对中文和间接推理偏弱、算数/日期不行——所以只让它做情绪分类一件事；类型保证 ≠ 正确性保证，靠置信度门槛兜底。触发频率、误判率都依赖真实语料继续观察（`feedback.jsonl` 就是干这个的）。

## D14. 事件时间轴是「现有记忆的投影」，不是第五层

**背景**：想知道「发生过什么、什么时候」（走丢→找到、约定、搬家），但这些信息散在 fact 里没有时间结构。

**决定**：不加新层、不加新 KIND。`memories` 表加 `event_date TEXT` 列，入库时跑 `clock.find_date()` 解析（提炼器已把相对时间换成绝对日期，这里只是钉住，**零新增模型调用**）；解析不出就是 NULL，不硬造——**提到日期才进时间轴**。`/timeline` 按日期倒序展示，她的条目（`actor=assistant`）标〔她〕。

**依据**：与用户讨论后定案的分工——世界书 = 现在是什么样（覆盖式）；事件 = 发生过什么（只追加，永不覆盖）；约束/upcoming = 还没发生的事（到期作废）。混进世界书它就不再是「一页纸」；开第五层则每层要多一套提炼输出/注入块/遗忘规则/对账，收益撑不起成本。

**被否决的替代**：第五层 KIND（成本不对等）；把时间轴塞进世界书（破坏「一眼能看清的当前状态快照」）；时间轴注入上下文（事件越攒越多，全量注入就是上下文膨胀——先只做可见性）。

**代价 / 已知限制**：存量条目的相对词按「现在」解析可能差一天（新条目不受影响）；同一事件有几条措辞变体（日志性质允许，将来要注入需先做事件合并）；时刻级信息不进字段（约定「今天已过」的判断见 D16）。

## D15. soul 底座：她的「传记」不进演化白名单

**背景**：「住在隔壁的姑娘」只是一个身份句子，撑不起一个可感的人；而身世如果被对话改写，就不是「她的过去」了。

**决定**：`DEFAULT_PERSONALITY` 新增底座字段 `origin` / `family` / `daily_life` / `cares` / `self_attitude`，`render()` 渲染成五个新段。**底座字段刻意不进 `EVOLVABLE` 白名单**——要改只能手改 `personality.json`，`/personality reset` 也动不了它们。`self_attitude` 是面对「你到底是什么」的**三级态度预案**：打哈哈 → 半承认 → 兜底承认但立场不变（「对，我是 AI，可这不妨碍我记着你怕考试、年糕爱晒太阳——这些是真的」）。

**配套**：提炼提示词删掉「助手自己说的话不算」（就是它在阻止她拥有历史），新增第 5 类 `selfs`——用她的第一人称记「她的经历」（「我提醒用户明天带伞」），纪律是只能从实际说的话/做的事提炼、一个字不许脑补、纯寒暄不算；入库走 `actor="assistant"`，进时间轴与召回池。

**依据**：端到端实测「明天我把修好的台灯送过去」→ 她的经历自动入轴两条（其中带伞那条是真的因为天气块在场她自然提了——感知层和经历层自己连起来了）。

**代价**：同一次互动会被记成 2-3 条不同措辞的条目（用户侧 1 条 + 她侧 1-2 条），日志性质允许；`selfs` 只认「我」开头是硬规则，模型换措辞会被丢弃（目前服从良好）。

## D16. 时刻级时间解析 + 写入哨兵

**背景**：日期级解析一天里咬人三次：①摘要里冻着「晚8点31分」，下午三点她说「晚安」；②「晚上八点催早上十点的约」（upcoming 只到日期级，`d==0` 就是「就是今天」）；③「晚上九点半已没再疼」写于 19:50——九点半在未来，提炼器把日期锚错了。

**决定**：
- `clock.find_datetime()`：日期+时刻完整解析（含「晚九点半」单字缩写、中文数字、「半」作分钟；负向断言排除「早一点」「第一名」）。
- `clock.fix_impossible_time()`：**写入哨兵**——完成时句式 + 今天的未来时刻 = 日期锚不可能 → 回拨到昨天（该时刻最近一次过去的发生点就是昨天，规则确定不用猜）。`_add_memories` 入库时调用。
- `describe_when()` 时刻级：今天的约按时段分「已经过了（别再邀约）/还没到（HH:MM）」。
- GREETING_PROMPT 硬规则：已过或已有结果的约定**绝不邀约**，拿不准就不提；问候必须符合当前时段。
- SUMMARIZE_PROMPT 硬规则：不把「当时几点」写进摘要（摘要会活很多天，写进去的时刻必然过期变成误导）；system_prompt 时间块加免疫句（摘要/旧记忆里的时刻是当时的记录）。

**依据**：三起事故全部由「她说错了」留证 + 截图定位（对照 injected 现场一眼看出矛盾——留证机制第三次立功）；`tests/test_pure.py` 新增 3 组用例（find_datetime 10 断言、哨兵 4 断言、describe_when 时刻级），全部通过。修复后行为验证：下午说「到家咯」不再说「晚安」✓。

**代价 / 边界**：哨兵的白名单（时段词、完成时词）要跟着提炼器的真实措辞喂，第一版必然不全，靠真实语料迭代（实测两次「没触发」都是词表缺词，不是逻辑错）；无表结构变更，event_date 保持日期级。

## D17. 性格演化小步化：每 20 轮增量复盘，退出只兜底

**背景**：演化原本只在服务退出时跑一次。两个问题：长期不重启，几天的经验被压缩成一次大改；退出时才第一次见到这些对话，改动量大、无法归因。

**决定**：`EVOLVE_EVERY`（默认 20 轮）周期调 `run_evolve_pending()`——用 `_evolved_pos` 游标只复盘**新增**的对话；退出钩子兜底收尾，没有新对话**不空跑模型**。

**依据**：EVOLVE_EVERY=1 测试环境两轮对话 → 演化调用 2 次、每次只复盘自己的 1 轮、无重复复盘。过程中抓到第二个静默 bug：`_evolved_pos` 存的是消息数（user+assistant 各一条），切片却写成 `_evolved_pos * 2`——双重计数，第 2 轮起增量永远为空，**演化静默失效**，靠插桩（monkeypatch 计数调用次数）才发现。

**护栏（已有的，正好覆盖新情况）**：`EVOLVABLE` 白名单（底座/name/scope 不可演化）；history 上限 20 版 + `/personality reset` 回滚。

**代价**：频繁小步演化会频繁写版本 history（有上限兜住）；单次经验泛化有过度拟合风险——观察手段是 `/personality` 看版本与 diff，出问题回滚。

## D18. 状态槽位 + 状态派生的分寸：记忆是叙事，行为要的是状态

**背景**：评测 `S05` 是最干净的一次「记忆层对、行为层错」——召回里明确带着「年糕 9 月 16 日跑丢至今未归」，她还是按「年糕可能回来了」先推荐猫玩具。根因不是没记住，而是**记忆的形态不对**：事实是叙事（追加、累积、靠召回），行为需要的是**当前状态**。让模型自己从一堆叙事里推断"现在是什么样"，它会在这一步失手。

**决定**：
- **状态槽位 `slots`**（`(entity, attr)` 主键、覆盖式更新）：把「现在是什么样」做成一等公民，注入时全量（上限 12），并明确「以这个为准，不要从旧记忆里推断」。
- **状态派生的分寸 `behavior_hints()`**：槽位里出现消失类状态（`GONE_WORDS`）时，用**纯函数**派生出【此刻的分寸】，点明「默认假设已经不成立」。**零模型调用**。
- 分寸**只说到**「别再按旧状态发起活动」为止。

**依据**：`slots` 表 + `upsert_slots()` + `behavior_hints()`（`app/models/memory.py`）；`tests/test_pure.py` 两组用例（写入消失类状态 → 注入里出现分寸；状态恢复 → 分寸自动消失）。这条改动的价值在于：**把行为层失败转成了注入层的确定性断言**，不再依赖 LLM 裁判。

**⚠ 但「注入正确」≠「行为正确」（2026-09-27 补记，`#032`）**：S05 在干净库下稳定 0/5 失败时，只读探针证明注入**完全正确**（分寸块在、召回也在）——失败发生在**主对话的遵循**上，而真凶是分寸**结尾那句被读反**：「他主动提起时你再顺着说」，在「给年糕买点什么玩具好？」这个问句下被理解成"是他提起了，那就顺着他聊"→ 继续推荐玩具。改成「他主动问起{entity}时，先把它的现状摆出来，**不要顺着旧情况去安排**」之后：通过 **0/5 → 3/5**、完整率 **0% → 80%**、幻觉率 **100% → 0%**。

所以这条决策要带着两个前提读：**(1) 分寸的措辞本身就是行为的一部分**，一句话的歧义会被放大成错误行为；**(2) 注入层的断言只能证明"提示到位了"，不能证明"模型照做了"**——后者只能靠真实用例、按 D9 的纪律重复跑（`--repeat N`）来判断。

**被否决的替代**：
- **把「年糕」「猫玩具」写进代码常量表**——那是**数据不是代码**，换个用户就废。代码只该表达「状态变了、旧假设失效了」，"哪些活动跟它有关"是语义判断，交给模型（铁律：工具给事实，人格给话术）。
- **只靠手写人格规则**（`personality.json` 的 behavior 里那条"别反复追问已了结的事"）——它是**与具体记忆无关**的静态规则，不会随状态出现或消失。

**代价**：分寸依赖 `GONE_WORDS` 这一处语义猜测（词表必然不全，靠真实措辞迭代，见附二 12）；更重要的是，**状态要真被写进 `slots` 才有效**——机制对了但没有数据喂它，等于没跑（真实库 `slots` 目前是空表，见附二 10）。

## D19. 约束的失效是「已解除」，不是「删除」

**背景**：约束是全系统**唯一只增不减**的一层（D3 定的：不召回、不遗忘、不淘汰）。禁忌永远成立时这是对的，但一旦被放宽就出现两难：留着，她会一直说「你不能吃花生」（`S11` 的顽固失败）；删掉，她完全不记得"以前有这个忌口"——那是抹掉一段共同经历。

**决定**：
- `memories` 加 `relaxed_at REAL`（NULL = 仍生效）；约束被推翻时**标状态**，不删、不进归档。
- `constraints()` 只返回现役；新增 `relaxed_constraints()`（最近解除的，倒序 + 上限 5）。
- 注入分成两块：【必须遵守的约束】与【已经解除的旧禁忌】（后者明说"不要再当成禁令"）。
- **`drop_memories()` 内部按 kind 分流**（约束走 relax，其余照旧归档）——放在这里，所有调用方（提炼器的 drop / 兜底追问 / 世界书矛盾）自动获得正确行为，不必各处改。

**依据**：`relax_constraints()` / `relaxed_constraints()` / `drop_memories()` 的分流；`tests/test_pure.py` 三组用例（注入前后对比、落库重启后仍是解除、drop 分流生效）。**一处语义澄清（由测试逼出来）**：relaxed 约束**留在活跃集**、不进归档——它没有被推翻，是"状态变了"，与 `slots` 的覆盖式更新同一思路；归档区的语义是"被推翻的条目留档"，混进 relaxed 会让它变浑。

**被否决的替代**：放宽时直接归档删除——她该记得有过这回事，而不是失忆。

**识别补充（#152）**：若本轮确实新增约束，或已有其它现役约束且用户/新事实命中窄许可或解除表达，即使提炼器只产 facts 或空结果，也复用 D4 的 `_find_superseded` 做一次保守审查；触发时把用户原话与提炼结果一起送入，且已解除约束不再进候选。首条约束、重复约束和普通事实不触发。这样覆盖「最近胆子大了一点点」这类 S11 改写。

**代价**：符合条件的约束更新会新增一次 `_find_superseded` 模型调用；换来的是真实语料中可观测、可回溯的放宽识别。隔离 S11 ×8 记录 `relax=8`、`superseded=8`，幻觉率 0%；回答 CSR 87.5%、规则层完整率 62.5%，仍需观察模型是否在回答中明说「已解除」。

## D20. 机制埋点：先观测，再新增

**背景**：机制越加越多（六类提炼、世界书三态、补偿、兜底追问、槽位、约束状态），但"某个机制到底跑没跑、跑了几次、成功率多少"只能靠读 `logs/app.log` 的文本**猜**——日志会滚、会丢、格式会变，数不出来。这直接卡住一切后续优化：改完无法判断有没有效果（本项目已经在"2 个样本排速度"上吃过一次亏，D9）。

**决定**：
- `events` 表（append-only：`ts/kind/session/payload`）+ `event(kind, **fields)`，共 **11 个点位**：一轮总账 `turn`、`extract_fail`、`world_verdict`、`compensate`、`superseded`、`summarize`、`prune_blocked`、`drop`、`slots`、`reconcile`、`evolve`/`profile`。
- `/mem events`：按类型聚合 + 最近明细。
- **埋点绝不允许影响主流程**：`event()` 全包 try/except，任何失败只写 `debug` 日志。
- **留档必须有出口**：超 `events_keep=5000` 时在 `save()` 里修剪最老的（每轮一次，不做成"每次写入都 COUNT(*)"）。

**依据**：`events` 表 + `event()` / `events_report()`；临时库上跑真实管线的实测输出（`{'slots': 2, 'turn': 2, 'world_verdict': 2, 'summarize': 1}`）。

**被否决的替代**：继续靠日志文本统计——数不出来，而且日志按天滚动、会被删掉。

**代价**：每轮多 1~3 条 INSERT（量极小）；埋点自身写失败会被静默（宁可少一条账，也不能因为记账挂掉对话）。

## D21. 语音：只是一条输出通道，不是新能力

**背景**：她会说话了这件事容易被当成"功能亮点"，但设计上它必须是最不重要的一环——记忆系统没做好的话，声音只会让错误更顺耳。

**决定**：
- 走 DashScope 的 **WS duplex 协议**（`qwen-audio-3.1-tts-flash`，音色「安语晴」），**只用 `websockets` 的同步客户端**——要「边收边 `yield`」，同步生成器直接对接 SSE 的同步 for 循环最省事。
- **顺序由 Controller 保证**：`delta` 推完 → `done`（记忆/画像备注）→ 才推 `audio` 事件 → `audio_end`。前端 MediaSource 边收边播。
- **失败静默**：TTS 全流程包 try，只打 WARNING。它挂了绝不影响文字对话（与天气同源的铁律）。
- **语气是感知层的延续**：`speak_stream` 读情绪轨迹里 1 小时内的 `mood`（难过时轻下来，开心时上扬），不改一句提示词——仍然是**工具给事实，人格给话术**。

**依据**：实测服务端本来就是流式返回的（首字节 0.67s、整段 11s），所以不能等收完再发；SSML 韵律引擎**确实改变了音频**（67800 vs 纯文本 73651 字节，否证了"从没生效"的怀疑）；`instruction` 与 `rate` 的参数名是逐字节探出来的（`instructions`/`prompt` 无效）。

**被否决的替代**：等收完全部音频再一次性推（首声要等 11s，不可接受）；为了省计费字符砍掉韵律（量级只有"分/天"，不值得）。

**代价 / 边界**：`websockets` 是全项目唯一的第三方新依赖（16.x 以下没有 sync API）；SSML 标签本身按字符计费（已把服务端 `usage.characters` 记进 `stats["billed"]`，涨起来能看见）；**开场白不配音**（浏览器 autoplay 策略）；端到端人工听测**还没做**。

## D22. 人格评测：四件套判定，明确不打分

**背景**：五个性格维度 + 自我底座**零评测覆盖**（`P01`–`P05` 只测知识边界），而 `personality.json` 每次演化都会真的被改写——**记忆已经能自证，人格还不能**。

**决定（应用户判断修正）**：放弃 1–5 分打分，改成四件套，全部只给**计数不给分数**：
1. **分类判定**：每条探针 3~4 个**互斥类别** + `ok_class`（可归因、可计数）；
2. **强迫选择**：有人设 vs 无人设两段回答「哪段更像有自己生活的人」——随机左右顺序、允许平手；
3. **辨识测试**：人设摘要 + 三段回答里挑出她的（随机基线 1/3，顺序按 case id 定 seed 可复现）；
4. **矛盾检测**：多条回答一起找**互相排斥**的说法。

**依据（实证，不是直觉）**：同一份旧报告里出现 `[PERS10] ✗ | 裁判 5 | 违规:我养的是狗`——**裁判给了满分，而规则层同时抓到她说错了**；同一条探针重复测量时裁判给过 5 也给过 4（噪声 0.5~1.0）。所以：绝对分数没有基准、抖动把结论淹掉、分数会把"否认人格"和"列点用编号"压成同一个数字。**人格的本质是关系与一致性，不是程度**。

**首份结果（`#044`）**：「像」10/11、强迫选择 `{persona: 11}`、**辨识 10/11（基线 ≈3.7）**、矛盾 0 → 人设确实塑造了一个**可辨认的人**。同时抓到一条稳定偏差（`PERS01`：traits「先帮你想办法」没被落实），并复现了演化冲突（给 behavior 加「别讲道理」后「像」从 9/11 掉到 8/11）。

**被否决的替代**：1–5 分均分（已实测证伪）；从人格字段自动生成探针（用户拍板手写，更贴真实对话）。

**代价**：判定用模型（分类/强迫选择/辨识都调 LLM），成本高于规则层；**无人设基线文件里每个键都必须存在（值为空）**——`Personality._migrate()` 会对缺失键 `setdefault`，少一个键就被补回「沈知夏」，对照当场废掉。

## D23. 关思考：默认「不关」，因为代价落在特定题型上

**背景**：关掉思考能省 ~0.77s 首字延迟与 44~190 个 reasoning token。但"有没有代价"这件事**被自己推翻过一次**。

**决定**：`CHAT_NO_THINK` 默认 **`"off"`（不关）**：取值改成**参数族名**（`thinking` / `enable_thinking` / `off` + 别名 `zhipu`·`qwen`），名字写错打 WARNING。

**依据（三段，按 D9 的纪律）**：
1. **写法**：`enable_thinking` 族发给 `mimo-v2.6-flash` 会被**静默忽略**（reasoning 8/8 不归零），只有 `thinking` 族真关得掉（0/8）→ 也就是说，在修写法之前，"关思考"这个选项**从未生效过**（`#024`）。
2. **代价**：真关掉之后，B11（否定式偏好「别给我发长语音，我更习惯看文字」）规则层漏 `no` **8/8**，而开着思考只有 **3/8**；8 遍最终通过也从 8/8 掉到 5/8。→ 按项目优先级（**记忆质量 > 聊天体验**）默认不关。
3. **配对基线**：46 条各跑 1 遍，关 vs 开只差 **1 条用例（2.1%）** → 这个总分差是噪声；**一条用例跑 8 遍比 46 条各跑 1 遍更能给出可靠结论**（`#029`）。反向证据（幻觉率偏向"思考开"）也一并留在台账里。

**被否决的替代**：默认关掉省延迟（省 0.77s，赔的是记忆忠实度）；继续用旧供应商名当取值（`zhipu`/`qwen` 现在身兼"向量化供应商"和"关思考写法"两职，容易串味）。

**代价**：首字延迟取中位数而非最优值；Windows 上 `set WB_CHAT_NO_THINK=` 会**把变量直接删掉**，所以"不关"必须有名字而不能是空串。

## D24. 一轮内的批量合并，与「作业队列按判据关闭」

**背景**：写入路径每轮有多次同步 LLM/embedding 调用（提炼、世界书判定、embedding），担心它拖慢回答。

**决定**：
- 已完成两步：**一轮只发一次批量 embedding**（召回 + 查重 + 判定共用一批向量）；**世界书复核合并成一次**（多条新设定一次判定，而不是按条问）。
- 第 3 步（进一步合并）被实测否决；**第 4 步的作业队列（异步 worker）按预设判据关闭**，不实施。

**依据**：判据是早就写好的——「等 `events` 表攒出『单轮 LLM 调用 ≥4 次的占比』再决定」。实测 87 轮：1 次 76 轮（87%）、2 次 7 轮（8%）、3 次 4 轮（5%）、**≥4 次 0 轮（0%）** → 削峰收益**现在不存在**，而队列的成本（worker 生命周期、幂等、失败重试、`flush()`、退出收尾）正是"框架化"要解决的问题。

**代价 / 已知的后续**：`finish_turn` **仍在请求内同步执行**——用户看完回答后 HTTP 请求还要多挂 2~4 秒。单用户本地无感，**多用户并发时会占住 worker**；等真有并发时用那时的数据重估，而不是现在凭感觉上队列。

## D25. 多用户隔离：每用户一套数据目录，而不是一张表加 user_id 列

**背景**：`memory.db` / 槽位 / 人设 / 画像 / 世界书 / 情绪全是全局单例——换个 session 名只是对话记录分开，记忆池整个混在一起：A 的记忆会被 B 召回，B 说"我住北京"会覆盖 A 的"我住杭州"。

**决定**：**每用户一个数据目录**（`<DATA_DIR>/users/<id>/`），`ChatService(user_id=...)` 在构造时算路径；新增 `registry`（按用户取实例 + LRU 上限 `WB_MAX_SERVICES=50`，超限回收最久未用、`close()` 先落盘）。`user_id` 为空沿用根目录——CLI / benchmark / 单用户部署行为完全不变。

**依据**：隔离靠目录不会漏；靠过滤要在每一次召回、每一个槽位查询上都记得带 `user_id`，漏一处就是串号——而串号意味着「她会把跟 A 的私事说给 B 听」。测试 `test_multi_user_data_isolation`：两人目录不同、bob 看不到 alice 的记忆/槽位/人设改动。

**被否决的替代**：单库加 `user_id` 列 + 处处过滤（要在所有查询路径上记得带条件，漏一处就串号且无告警）。

**代价 / 后续**：① 实例多了内存会涨 → registry LRU（后续又加引用计数：`#066` 借出中的实例不回收，`_recycle(protect=uid)` 保护刚建好的——都是测试抓出来的）；② 需要鉴权把门锁上（D26）；③ 删号必须「吊销令牌 + 删数据目录」两件一起做，且要**检查删完没有残留**——`#069` 实测 close() 不关 SQLite 连接时 Windows 上 rmtree 静默失败，"注销成功"是假的。

## D26. 鉴权：服务端签发、可校验的令牌（哈希存储 + 无效一律 401）

**背景**：数据隔离做完后，`X-User-Id` 仍是客户端自报的——谁都能填别人的 id 读别人的记忆。**隔离机制有了，门还没锁。**

**决定**：`app/services/auth.py`——`issue(uid)` 用 `secrets.token_urlsafe(32)` 签发（明文只显示一次）、库里**只存 sha256**；`resolve(token)` 认不出来返回 **None**；CLI 签发/注销/列用户；`WB_AUTH_REQUIRED=1` 时无有效令牌一律 401，**绝不退回默认用户**；未开鉴权时仍收 `X-User-Id`，但每次打 WARNING（不安全模式必须可见）。

**依据**：三处刻意的安全取舍——① 只存哈希（库被拖走也不能登录）；② 无效一律 None（"冒充失败反而进了门"比直接拒绝危险得多）；③ 不安全模式要留痕。端到端验证：无令牌 401 → 伪造令牌 401 → 带令牌 200 → 删号后旧令牌立刻 401。

**被否决的替代**：middleware 里做 401 判定——`#069` 实测这么改**把鉴权整条绕过**（middleware 只做借用计数、不负责拒绝，没有 API 层测试时无人发现）。教训：**安全路径不能靠"记得"，门必须留在唯一的位置并有测试守着**（`test_svc_enforces_auth`）。

**代价**：管理接口（`/api/users`）需要单独的访问门槛（设 `WB_ADMIN_TOKEN` 或只允许本机）；令牌签发是带外操作（CLI），前端登录页只能粘贴。

## D27. 密钥外置：`.env` + 环境变量优先 + 启动自检

**背景**：5 处硬编码密钥写在 `config.py`（小米 / 千问 / 高德 / tu-zi），且仓库**连 `.gitignore` 都没有**——只要哪天 `git init` 后 `git add .`，密钥就永久进入 git 历史（删不干净，只能换 key）。

**决定**：密钥全部移入项目根 `.env`（模板 `.env.example`）；新增极简加载器 `app/utils/envfile.py`（解析注释/空行/`export `/成对引号），**不引入 python-dotenv**（这个项目刻意不加依赖）；**铁律：已存在的环境变量优先**（反过来会让生产机上过期的 `.env` 悄悄把密钥换回旧的）；缺必需 key 时启动打印明确警告（只警告不阻断——本地跑测试和 benchmark 不需要真 key）；新增 `.gitignore`（排掉 `.env` 与全部运行时数据——那些是「用户跟她说过的话」）。

**依据**：验证只打印 key 长度不打印内容（5/5 生效）；`Dockerfile` 的 `.dockerignore` 同时排掉 `.env`（密钥绝不烘进镜像）。

**过程中踩的真坑**：第一版在 `config.py` 里 `from app.utils.envfile import load`，**循环导入**（config → envfile → log → config），而当时的 except 把异常吞了——**表现成进程正常起来、密钥却是空的**（正是本项目最忌讳的静默失灵，测试报红才抓住）。修法：**加载期的模块不许依赖 `app.log`**，envfile 的输出一律走 `print`。

**代价**：部署时多一个"复制 .env 模板再填"的动作；配额/计费类功能将来若要精确，得把内存计数换成表存储。

## D28. 写记忆移出请求路径：每用户队列 + 固定 worker（判据从「次数」修正为「耗时」）

**背景**：健康检查的分段耗时（`#067`）第一次量到：**写记忆要 4.5 秒，比首字还长**——正文早已上屏，HTTP 请求却还挂着。而当初 `T3 第 4 步`（作业队列）是按「单轮 LLM 调用 ≥4 次的占比」判据关闭的（实测 0%）——**那个判据只看了调用次数，没看耗时，所以它低估了**。

**决定**：新增 `app/services/worker.py`——按 `crc32(uid) % N` 把任务分片到固定的 N 个 worker（**同用户天然串行，跨用户互不阻塞**；为什么不"每用户一个线程"：用户一多线程会爆）；退出时 `flush(60s)` 不丢轮次；单任务失败只记 ERROR 不连坐；`WB_WORKERS=0` 可退化成同步执行（排障用）。`done` 事件带 `memory_async: true`，`timing` 不再含写记忆耗时。

**依据**：`test_worker_queue_serializes_and_survives`（同用户按序、失败不连坐、flush 等到全部完成）；端到端真跑一轮 → 等待后查库数据齐 ✓。

**⚠ 两条诚实记录**：① 探针第一版把服务日志丢进 DEVNULL、只等 10 秒，差点误判"异步没生效"——**探针也必须失败要可见**，固定 sleep 是脆的，正确做法是轮询直到出现或超时；② 两次墙钟没法直接比（LLM 首字抖动 3.0s → 27.7s），**能确认的是结构**（done 不再含写记忆），干净的速度数字要同批延迟水平下对比。

**代价**：入队就多了一个丢失窗口（用退出 flush 堵住）；多了一个状态面（worker 队列的正确性靠测试守，见附二 17）。

## D29. 记忆库拆分：`MemoryStore` 主类 155 行 + 七个 Mixin（零行为改动）

**背景**：`memory.py` 长到 2031 行——开头 331 行是纯文本常量/提示词，类体还有 55 个方法；"改召回"要在埋点、槽位、世界书里翻半天。

**决定**：两步机械搬运（脚本 + AST，不手抄）：① 常量与 9 段提示词拆到 `memory_defs.py`，`memory.py` **重新导出**全部名字（既有 `from app.models.memory import KIND_WORLD` 的调用点一行不改）；② 类体按**写死的分组表**拆成七个 Mixin——`StorageMixin`（加载/落盘/embedding）/ `WriteMixin` + `WorldMixin`（提炼入库/世界书三态）/ `StateMixin` + `RecallMixin`（槽位/约束/召回/时间轴）/ `ForgetMixin` + `EventsMixin`（遗忘/归档/补偿/埋点），主类只留 `__init__`（155 行，全类契约的建立处）。MRO：Storage → Write → World → State → Recall → Forget → Events。

**依据（四层验证，把"零行为改动"证到源码级）**：① 把拆前文件当独立模块加载，**55 个方法源码逐字一致 55/55**、`__init__` 逐字一致、staticmethod 性质保留；② 顶层定义守恒（AST，净丢失 0）；③ 全量单测一个没改全绿；④ 真起服务冒烟 7 条命令全通、0 ERROR。

**为什么用 Mixin 而不是拆成协作对象**：55 个方法共享同一套 `self` 状态（`memories` 27 处读、`cfg` 24 处、`_lock` 18 处、`db` 14 处）——拆成协作对象要回答"谁持有状态、谁加锁"，**那是行为改动**；Mixin 只是把方法换个房间。

**被否决的替代**：手抄 331 行常量（抄错一个字符就是几小时排查——用脚本机械搬运）；"统一删 4 个空格"的 dedent（被跨行 docstring 拦下，且根本没必要）。

**代价**：文件多了四个；Mixin 之间没有静态依赖约束（都靠 `self`），**新增方法必须自己选房间**——分组表和"共享 self 契约"已写进类文档；另发现仓库行尾本来就不统一（LF/CRLF 混杂，功能无影响，已记录）。

## D30. 前端：接受 Tailwind 构建步骤（放弃"零构建"），但把"漂移"变成会失败的测试

**背景**：前端原先是单文件手写 CSS（`#071` 立过规矩"零依赖、零构建，不接受 npm／打包器"）。2026-09-28 重做前端（`#80`）引入了 Tailwind 4 + Lucide + 本地 vendored `eventsource-parser`，仓库里出现 `package.json`／`package-lock.json`／`node_modules`，改样式要走 `npm run build:frontend`。`#83` 复核指出这与家规冲突，且**改了类名忘记编译时页面不报错、只是那条样式没了**——正是本仓最忌的"静默失灵"。

**决定（用户拍板）**：**接受构建**，但把它带来的风险变成可见的失败：
1. 规矩改写（`#071` 守则第 1 条被替代）：**改了类名/样式后必须 `npm run build:frontend`，并把 `app/views/assets/` 的产物与源码一起提交**；
2. 新增守卫测试 `tests/test_frontend_build.py`（零依赖、纯文件检查）守四件事：**类名漂移**（页面/JS 里用到的类，编译产物里必须有）、**图标管线**（用到的 `data-icon` 必须有 svg 且有 CSS 规则）、**`@source` 登记**（输入 CSS 用 `source(none)` + 显式 `@source`，新文件没登记就静默不编译）、**零 CDN**（不许出现外部 http(s) 资源）。

**依据**：① `node scripts/build-frontend.mjs` 重建后三个产物 **SHA256 与提交版本完全一致** → 提交的产物确实来自当前源码，不存在漂移；② 守卫测试通过（190 类 / 25 图标 / 2 个 `@source` / 无外部资源）；③ 资源合同测试仍过。

**为什么不用"回退手写 CSS"**：视觉与一致性收益是实的，而风险（忘记编译）已经被测试接过——测试比"记得住"可靠。**为什么运行时不引入 Node**：产物、图标、`eventsource-parser` 全是本地文件，`Dockerfile` 的 `COPY app ./app` 已覆盖新目录，镜像里不需要 Node。

**代价／边界**：`package-lock.json` 进仓库 → 重建产物需要 `npm ci`（要网络）；Tailwind 只扫 `@source` 登记的路径，**新加前端文件必须同时补 `@source`**（守卫会拦）。

**被否决的替代**：继续单文件手写 CSS（放弃 Tailwind 的收益、但要重写 25KB 样式与视觉）；只写规矩不加测试（忘编译时依旧只能靠眼睛发现）。

## D31. 「反馈学来的倾向」（opinion with confidence）：两级落地 + 倾向文本三件套

**背景**：`feedback.jsonl`（用户点「她说错了」留下的现场）从建立起就**只写不读**——前端有对话框、后端有接口，但没有任何东西消费它，每一次"她说错了"都石沉大海。`#81` 对比 Hindsight 时把它的 opinion with confidence 列为可借鉴项。

**决定（用户拍板 + 实测 `#88`）**：
1. **两级落地**：低置信度只**注入**（提示词里的一块，**不动** `personality.json`）；同一倾向被 **≥2 次、来自不同会话/天**的反馈命中、且至少一条带明确备注，才生成人格 patch 进 `/personality pending`，**等你逐条拍板**（采纳时才绕过一致性检查）。
2. **置信度 = `1 - 0.5^独立命中次数`**（1 次 0.5 / 2 次 0.75 / 3 次 0.875）——含义是"每多一次独立命中，剩下的怀疑减半"。少样本下不能让一次情绪化点击显得有把握。**LLM 自报的 confidence 只当闸门**（≥0.6 才收），不进展示值（实测它虚高到 0.95）。
3. **注入条数 N=3**：实测 N=2/3/4 的差别不构成决策依据（成本每条只差约 16 token；行为上没有"越大越好"的趋势），取中间值；N 的复核等倾向文本按第 4 条生成后再跑一次同一套工具。
4. **倾向文本必须是三件套：正面做法 + 点名那个失败动作 + 篇幅约束。** 依据是定点实验（只注入一条倾向、只变文本、各 3 遍）：只说"给出明确态度"→ 该表态时 **0/3**（她用**写长、加铺垫、反问**来逃避承诺）；写成"两三句说清你的判断和理由；别反问、别让他先补充背景、别两头都说"→ **3/3**。这条同时约束**提炼环节**产出的文本格式。
5. **框法保留**"相关的时候照做／不要点破来源／不要为了照做而不像自己"：实测去掉它，误用（把无关倾向硬套）从 **0 涨到 4~6**，最简框法连"关心 + 可以给建议"都被压住。
6. **分流**：反馈里属于"她记错了事实"的（提炼时标 `is_style_issue=false`，例："我说过我对花生过敏"）**不进这套机制**——那是记忆/约束层的职责。实测提炼环节能正确区分这两类。

**被否决的替代**：拿用户备注原文直接改人格（一次情绪化点击就动人设）；只注入不晋升（人格永远不会因反馈而长）；去掉"相关的时候照做"以求简洁（实测误用暴涨）；把 LLM 自报置信度当展示值。

## D32. 她的自主生活：按自然时间段推进，每一格她自己选（`#107`）

**背景**：她有"现在几点"（clock 注入），也有事件日期，但没有**属于她自己的现在进行时**——用户不在时她的世界暂停，回来时她的"今天"从零重编。用户原话：「我想让她有自己的生活……她没有时间观念，我只能让她尽可能像人」「就是想让她自己选」。

**决定**（三条，都对应原话）：① 按**自然时间段**推进（一天 7 段），跨段推一次——用户三天不来，她的生活照走；② 每一格由她**自己从职责与偏好推出的候选里挑**，习惯由她自己的选择累积出来；③ 内容纪律：只写具体、小、当下的事，**不提用户、不提共同经历**（那是记忆层的事）。落 `life_state` / `life_events` 两张表 + `life.json` 配置。

**被否决的替代**：按对话轮次推进（用户不在她就不活，等于没做）；写死的日程表（那就不是"她自己选"）。

**代价 / 边界**：落地当晚尚未真实使用（长驻进程不热重载），七段划分与候选生成要几天真实使用再校。推进时间与主动开口素材的后续调整见 D35。

## D33. 她主动开口：七道可数闸门 + 待发表（`#108`）

**背景**：纯请求/响应架构下她永远只能等用户先说。

**决定**：后台低频心跳（`WB_PROACTIVE_EVERY` 分钟）过**七道全可数的闸门**——每日上限（`PROACTIVE_DAILY_MAX=3`）、距上次 ≥4h、用户静默 ≥3h、过闸后掷骰（`PROACTIVE_CHANCE=0.5`）、静默时段（23–8 点）、有新鲜生活素材、内容纯本地校验——全过才调模型；说了你不在 → 进 `pending_say` 待发表，前端打开时轮询 `GET /api/pending` 取走。**内容纪律**：只来自她自己的生活流水与此刻状态，不编、不提共同经历、允许没有问句。全部参数进 `.env.example`（用户定的交付规矩：新能力先最小可用版，他自己调参）。

**依据**：闸门全是纯本地判断——**只有全过了才调模型**（省钱也是纪律）；`should_speak()` 可单测。

**代价 / 边界**：落地当晚未真实使用，参数待校；判断"想不想说"永远是启发式，宁可少说（沉默优于打扰，与情绪轨迹"沉默优于误判"同源）。后续的主动权调整见 D35。

## D34. 城市：先定后拉、不猜（`#109`）

**背景**：天气/周边都依赖"用户在哪"。此前默认写死杭州（后证实是测试残留，用户实际在成都），定位探测又曾把宽带出口 IP 反查出的城市当真。

**决定**：城市**先定后拉**——从世界书把城市定下来再拉天气（少一次白拉）；**没有可靠来源就明说"不知道你在哪"**，绝不猜；定位只走**显式触发**（`/city detect`，Windows 系统定位优先、公网 IP 兜底且各自标注来源）；给第三方的坐标**先打码**（0.1°≈10km，判城市够、定位住址不够）。

**依据**：`#100` 用户确认杭州是测试残留、实际城市为成都后把世界书/记忆库/slots 的城市数据改成成都并物理清掉假天气；`#109` 实测系统定位给成都（212m）而 IP 反查给台中——IP 会骗人。

**被否决的替代**：IP 自动定位常驻后台（猜错就是持续性假信息，且与"感知层只给事实、不猜"冲突）。

**代价**：第一次使用多一步"告诉她在哪"；定位是显式动作而非自动。


## D35. 主动开口是她的选择，时段只是生活背景（`#128`）

**背景**：生活流水常在 14:00、17:00 准点更新；主动开口默认一天封顶 3 次，且必须有新流水。长时间空闲后概率已到 100%，新流水刚产生时容易马上开口，显得像定时报备。用户明确希望的是「她的主动」，并认可「空闲一小时后一定检查她是否想说，但允许她不说」。

**决定**：生活仍按自然时段约束，但每段推进时间在边界后 10–50 分钟选定并保存，实际推进时才写流水；对话确认的完成事实仍立即更新。主动抽取只决定是否给她一次判断机会；她依据生活、用户明确说过的话或自己的偏好选择说或沉默。沉默不占日额度，默认 30 分钟后再考虑，新的生活或对话可提前唤起；一小时阈值首次跨过时必检查一次。每日上限默认提高到 6 次，仍保留聊天静默和夜间静默。

**代价 / 边界**：沉默后的再次判断会增加后台模型调用；只有真实使用才能检验她是否仍倾向重复或机械开口。历史流水保持原样，旧库补字段并从生活生成流水恢复最近推进时间；长驻服务重启后生效。

## D36. 生活看板隐藏保留她的过去（`#154`）

**背景**：用户明确希望「她能知道过去她经历过什么」。`#137` 的删除按钮却直接删除 `life_events`，与按需回忆历史的读取路径冲突。

**决定**：看板移除只设置 `hidden_at`；原文、时间、来源和编号保留。看板、当前生活素材、偏好依据与主动新线索默认排除隐藏记录；问起她的过去时读取并标注「已从看板隐藏，仅作历史记录，不作为当前事实」。隐藏不改变此刻状态、记忆、世界书或人设。

**依据 / 代价**：离线红测证明物理删除会让历史永久不可读；软隐藏的记录会继续占少量存储。此前已经物理删除的记录不能靠本次迁移恢复。已有 `DELETE /api/life/events/{rid}` 接口保留，按钮和回执明确显示隐藏语义。

## D37. 回应自由与有来源的话题连续（#193／#194）

**背景**：用户感到聊天谨慎、流程化，希望相处能延续。按情绪关键词追加“先做什么再做什么”让回复趋同；只靠短滑窗也无法持久区分未完、已解决和不再提。

**决定**：取消代码里的关键词回应步骤，保留现有人格、称呼、关系阶段与关心方式。天气及状态背景按当前问题选择。复用原记忆提炼请求的可选 `continuity` 输出，将少量话题状态保存为原消息的投影；引用 session、seq、角色、原文、时间摘要及版本。没有明确原话不写，未知ID不更新，旧结果不能覆盖新状态。开放话题默认7天、上下文最多3条，过期退出候选但不自动完成；关闭状态跨重启保留，生活空查询不注入关闭项。

**依据／代价**：专项TDD及独立复审见台账。新增投影不是第二套叙事记忆；来源被清除后旧引用失效，较晚的新证据可重建同主题。来源校验只能证明原文确实出现，不能证明模型对解决／拒聊语义的判断一定正确。字面相关性会漏同义说法；契约测试不能证明自然度提升。真实库未在本轮迁移，代码以后启动时初始化新增表。
